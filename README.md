# Scout2Map - STM32F103C8T6 주행 제어 펌웨어

UGV 하부 주행 제어 MCU용 베어메탈 펌웨어다.
HAL과 RTOS를 사용하지 않고 CMSIS 레지스터 레벨로 직접 구현한다.

## 현재 단계

**주행 제어 실물 검증 완료.**

하드웨어 브링업, USB 링크, 폐루프 속도 제어까지 실물에서 검증했다.
150 mm/s 계단 입력에 대해 정상상태 오차 0.3%, 정착 760ms를 달성했다.

| 구성 요소 | 상태 |
|---|---|
| 클럭 72MHz / USB 48MHz | 검증 완료 |
| USB CDC 링크 | 검증 완료 |
| 바이너리 프로토콜 | 검증 완료 |
| 엔코더 분해능 5764 | 실측 확정 |
| 모터/엔코더 방향 | 실측 확정 |
| 속도 PID | 지면 튜닝 완료 |
| BNO055 IMU | 구현 완료, 실물 검증 대기 |
| 거리센서 (2D120X) | 미구현, 0xFFFF 반환 |
| 배터리 전압 감시 | 미구현, 0 반환 |

`config/board_config.h`의 `ENCODER_AVAILABLE`이 1로 설정되어 있다.

개루프 경로는 삭제하지 않고 폴백(fallback) 경로로 유지한다. 엔코더 배선이
단선되거나 신호가 유실되면 런타임에 자동으로 개루프로 전환되므로, 야전에서
로봇이 완전히 정지하는 대신 성능이 저하된 상태로 임무를 지속할 수 있다.

## 툴체인 구성

```
sudo apt install gcc-arm-none-eabi openocd
```

CMSIS 헤더는 용량과 라이선스 문제로 저장소에 포함하지 않는다.
클론 직후 1회 아래 스크립트를 실행한다.

```
./setup.sh
make
```

`setup.sh`는 ST의 디바이스 헤더와 ARM의 코어 헤더를 받아 `cmsis/`에
배치한다. 이미 존재하면 아무 동작도 하지 않으므로 반복 실행해도 안전하다.

`stm32f1xx.h: No such file or directory` 오류는 이 단계를 건너뛴 경우 발생한다.

### HAL을 사용하지 않는 데 따른 제약

본 프로젝트는 순수 CMSIS만 사용한다. CMSIS 디바이스 헤더는 레지스터
필드의 **마스크만** 정의하며, `RCC_CFGR_PLLSRC_HSE`처럼 특정 값을 나타내는
상수는 ST HAL에만 존재한다.

따라서 클럭 설정 등에서 값이 필요한 경우 RM0008 기준의 비트 패턴을
파일 상단에 명시적으로 정의하여 사용한다. HAL 예제 코드를 참고할 때
이 차이에 주의한다.

### 빌드 결과 확인

정상 빌드 시 다음과 같은 크기가 출력된다.

```
   text	   data	    bss	    dec	    hex	filename
  12056	      0	   1176	  13232	   33b0	build/scout2map_drive.elf
```

64KB 플래시 대비 약 18%, 20KB RAM 대비 약 6%를 사용한다.

## 빌드 및 업로드

```
make
make flash
```

ST-LINK V2 클론은 최신 STM32CubeProgrammer에서 거부되는 경우가 있으므로
OpenOCD 경로를 기본으로 사용한다.

## 디렉토리 구조

```
scout2map-fw-drive/
├── Makefile              # 크로스 빌드, 소스 자동 탐색
├── ld/                   # 링커 스크립트
├── config/
│   └── board_config.h    # 핀맵, 클럭, 튜닝 상수 (모든 계층이 참조)
├── app/
│   ├── main.c            # 협조적 스케줄러
│   ├── board_io.c/.h     # 제어 계층 <-> 드라이버 결선 어댑터
│   ├── calib.c/.h        # 엔코더 캘리브레이션 모드
│   ├── link.c/.h         # USB <-> 프로토콜 <-> 제어 결선
├── lib/
│   ├── hal/              # MCU 주변장치
│   │   ├── clock.c/.h
│   │   ├── systick.c/.h
│   │   ├── debug_uart.c/.h
│   │   ├── led.c/.h
│   │   ├── usb_cdc.c/.h
│   │   ├── i2c.c/.h
│   │   └── startup_stm32f103.c
│   ├── drivers/          # 외부 부품
│   │   ├── motor.c/.h    # BTS7960
│   │   ├── encoder.c/.h  # TIM1 / TIM4 쿼드러처
│   │   └── bno055.c/.h   # IMU, NDOF 융합
│   └── control/          # 하드웨어 비의존 로직
│       ├── drive.c/.h    # 기구학, PID, 오도메트리
│       ├── protocol.h    # 와이어 포맷 정의 (단일 진실 공급원)
│       ├── protocol.c    # CRC16
│       └── framing.c/.h  # 프레임 인코더 / 디코더
├── tools/

    ├── Makefile
    ├── test_drive.c
    └── test_framing.c
```

헤더는 대응하는 `.c` 파일과 같은 디렉토리에 배치한다. 모듈을 이동할 때
파일 하나만 옮기면 되고, 어떤 헤더가 어느 모듈 소속인지 즉시 드러난다.

`Makefile`은 `app/*.c`와 `lib/*/*.c`를 와일드카드로 자동 탐색한다.
새 모듈을 추가할 때 해당 디렉토리에 파일을 넣기만 하면 되며
Makefile을 수정할 필요가 없다.

### 계층 의존 규칙

```
app  ->  lib/control,  lib/drivers,  lib/hal
lib/drivers  ->  lib/hal
lib/control  ->  (없음)
config  ->  모든 계층이 참조 가능
```

**`lib/control`은 어떤 하드웨어 헤더도 참조하지 않는다.** 모터, 엔코더,
IMU, 시스템 클럭 접근은 전부 `drive_io_t` 함수 테이블을 통해 주입받는다.
결선은 `app/board_io.c`가 전담한다.

이 구조의 실익은 두 가지다. 첫째로 모터 드라이버나 엔코더 방식을 교체할 때
`board_io.c`만 수정하면 되고 제어 로직은 변경되지 않는다. 둘째로 제어
계층 전체를 호스트 PC에서 컴파일하고 실행할 수 있어, 보드 없이 기구학과
PID를 검증할 수 있다.

## 호스트 단위 테스트

크로스 툴체인이나 실물 보드 없이 제어 계층을 검증한다.

```
make test
```

세 개의 스위트가 실행된다.

| 파일 | 대상 |
|---|---|
| `test_drive.c` | 기구학, PID, 오도메트리, 엔코더 상수 |
| `test_framing.c` | 와이어 포맷, CRC, 디코더 복구 |
| `test_motor.c` | 슬루 제한, 데드타임, 슛스루 차단 |

`test_motor.c`는 `motor.c`가 타이머 레지스터를 직접 다루므로 로직을
전사하여 검증한다. `motor_update()` 수정 시 양쪽을 함께 갱신해야 한다.

기대 출력은 다음과 같다.

```
=== Scout2Map drive control, host tests ===

straight command produces forward duty     PASS
stale command stops both wheels            PASS
   settled speed=0.2000 duty=760 counts/loop=31
PID converges on the target speed          PASS
request above the gearbox limit is clamped PASS
in place rotation drives the wheels apart  PASS
   odom after 2s at 0.2 m/s: x=0.386 y=0.001 th=0.002
straight run accumulates x only            PASS
straight run leaves heading unchanged      PASS

ALL TESTS PASSED (0 failures)
```

테스트 하네스는 1차 지연 플랜트로 모터를 모사하며, RPi5가 `cmd_vel`을
연속 발행하는 상황을 재현하기 위해 매 루프마다 명령을 갱신한다.
명령 타임아웃 검증에는 갱신을 생략하는 별도 경로를 사용한다.

PID 게인을 수정한 뒤에는 실물에 올리기 전에 이 테스트를 먼저 통과시킨다.

## 만능기판 커넥터 배치

```
Distance Sensor(2D120X):
                    SIG
5V      GND         PA4                 : ADC12_IN4

L Motor Driver(BTS7960) + Encoder:
MD_+    MD_-    EN      L_PWM   R_PWM
5V      GND     PB0     PA0     PA1     : TIM2_CH1 / TIM2_CH2
E_+     E_-     E_A     E_B
3.3V    GND     PA8     PA9             : TIM1 encoder mode

R Motor Driver(BTS7960) + Encoder:
MD_+    MD_-    EN      L_PWM   R_PWM
5V      GND     PB1     PA6     PA7     : TIM3_CH1 / TIM3_CH2
E_+     E_-     E_A     E_B
3.3V    GND     PB6     PB7             : TIM4 encoder mode

IMU(BNO055):
                    SDA     SCL
3.3V    GND         PB11    PB10        : I2C2
```

### 엔코더 핀을 PB0~PB3에 배치할 수 없는 이유

하드웨어 쿼드러처 디코딩은 타이머의 CH1 + CH2 쌍에서만 동작한다.
F103C8T6에서 가용한 조합은 다음이 전부다.

| 타이머 | CH1 | CH2 | 용도 |
|---|---|---|---|
| TIM1 | PA8 | PA9 | 좌측 엔코더 |
| TIM2 | PA0 | PA1 | 좌측 PWM (점유) |
| TIM3 | PA6 | PA7 | 우측 PWM (점유) |
| TIM4 | PB6 | PB7 | 우측 엔코더 |

PB0/PB1은 TIM3의 CH3/CH4이며 엔코더 모드를 지원하지 않는다.
PB2는 타이머 채널이 아니고 BOOT1 핀이므로 리셋 시 Low를 유지해야 한다.
따라서 PB0/PB1은 EN(비상 정지) 용도로 유지하고, 엔코더는 위 표에 따라 배치한다.

EXTI 인터럽트를 이용한 소프트웨어 디코딩도 가능하나, 76RPM 주행 시
초당 8천 회 이상의 인터럽트가 발생하여 200Hz 제어 루프를 잠식하므로 채택하지 않는다.

### IMU 핀 변경 사항

BNO055를 기존 PB6/PB7(I2C1)에서 **PB10/PB11(I2C2)** 로 이설했다.
우측 휠 엔코더용으로 TIM4(PB6/PB7)를 확보하기 위함이다.
이 배치는 AFIO 리맵 설정이 불필요하므로 초기화 코드가 단순해진다.

## 엔코더 배선

| 선 색 | 역할 | 연결 |
|---|---|---|
| 빨강 | 모터 + | BTS7960 M+ |
| 흰색 | 모터 − | BTS7960 M− |
| 파랑 | 엔코더 VCC | E_+ |
| 검정 | 엔코더 GND | E_− |
| 노랑 | A상 (11 PPR) | E_A |
| 초록 | B상 | E_B |

엔코더 전원 범위는 3.3~5V이나 **3.3V 공급을 권장한다.** 출력 레벨이 3.3V로
정렬되어 STM32 입력에 가장 안전하다. 해당 핀들은 5V tolerant이므로 5V도
동작하지만 불필요한 여유는 두지 않는다.

빨강과 흰색을 바꿔 연결하면 회전 방향이 반전된다. 좌우 모터는 서로
마주보게 장착되므로 한쪽은 반대로 결선해야 정방향이 일치한다.
코드에서 `ENC_L_INVERT` / `ENC_R_INVERT`로 처리해도 무방하다.

## 구동계 제원

JGB37-520 12V 데이터시트 기준값이다.

| 항목 | 값 |
|---|---|
| 감속비 | 131 : 1 |
| 무부하 회전수 | 76 RPM |
| 정격 회전수 | 58 RPM |
| 정격 토크 | 15.0 kg·cm |
| 최대 토크 | 24.0 kg·cm |
| 무부하 전류 | 120 mA 이하 |
| 정격 전류 | 1 A 이하 |
| 스톨 전류 | 2.3 A |

데이터시트의 감속비 계열은 6.3 / 10 / 19 / 30 / 56 / 90 / 131 / 168 /
270 / 506 / 810 이며 **150은 존재하지 않는다.** 76RPM은 131:1 항목의
무부하 회전수에 정확히 대응한다.

설계 최고 속도는 **정격 58RPM 기준**으로 산정한다.

```
58 / 60 x 0.2073 m = 0.200 m/s
```

무부하 76RPM으로 산정하면 0.262 m/s가 나오나, 이는 실제로 도달할 수 없는
값이므로 제어기가 영구적으로 포화 상태에 놓인다.

전류 설계는 모터 4개 기준 스톨 9.2 A이며, 3S 6000mAh 팩에서 약 1.7C에
해당하여 25~35C 등급으로 충분하다.

## 엔코더 분해능 (실측 완료)

2026-08-13 실측으로 확정했다. 바퀴를 손으로 정확히 10회전시켰을 때
57640 카운트에서 임계값에 도달하여 11 PPR 가설이 검증되었다.
13 PPR이었다면 약 8.5회전에서 도달했을 것이나 그렇지 않았다.

| 항목 | 값 | 상태 |
|---|---|---|
| `ENC_PPR` | 11 | 실측 검증 |
| `GEAR_RATIO` | 131 | 실측 검증 |
| `COUNTS_PER_WHEEL_REV` | 5764 | 실측 검증 |
| `MM_PER_COUNT` | 0.03597 mm | 계산값 |

최고 속도 0.20 m/s에서 5ms 제어 루프당 약 27.8 카운트가 유입된다.
속도 PID 입력으로 충분하며, int16 래핑 한계(32768) 대비 약 1179배의
여유가 있어 제어 루프가 최대 5.9초간 지연되어도 카운트를 유실하지 않는다.

**모터를 교체하거나 재배선한 경우 `CALIB_MODE`를 1로 설정하여
재측정한다.** 이 값이 틀리면 속도 제어와 오도메트리가 모두 비례
오차를 가지며, SLAM 지도에 루프 클로저 불일치로 나타난다.

호스트 테스트(`make test`)에 이 값들을 검증하는 항목이 포함되어 있어
실수로 수정하는 경우 즉시 실패한다.

### 참고: 감속비 오류의 영향

감속비를 150으로 잘못 가정했을 경우 다음과 같은 오차가 발생했을 것이다.

```
5764 / 6600 = 0.873
실제 1m 주행 -> 87cm로 보고
```

SLAM 지도가 12.7% 압축되며, 복도 왕복 시 루프 클로저 불일치로 즉시 드러난다.

JGB37 계열은 11 PPR과 13 PPR이 혼재하여 유통되므로 모터 교체 시
반드시 재측정한다. 13 PPR인 경우 `COUNTS_PER_WHEEL_REV`는 6812가 된다.

측정 절차는 다음과 같다.

1. 차체를 들어올려 바퀴를 공중에 띄운다.
2. `encoder_reset()`을 호출하거나 보드를 리셋한다.
3. 바퀴를 손으로 정확히 10회전시킨다. 시작점 표시를 해두면 정확도가 올라간다.
4. `encoder_get_total()` 값을 10으로 나눈다.
5. 결과를 `COUNTS_PER_WHEEL_REV`에 직접 대입하거나, 역산하여 `GEAR_RATIO`를 수정한다.

좌우를 각각 측정하여 값이 크게 다르면 배선 또는 감속비 불일치를 의심한다.

## 엔코더 캘리브레이션 모드

`config/board_config.h`의 `CALIB_MODE`를 1로 설정하고 빌드하면
주행 대신 캘리브레이션 모드로 부팅한다. 이 모드에서 모터는 활성화되지
않으며, 양측 BTS7960의 EN 핀은 세션 내내 Low를 유지한다.

```
#define CALIB_MODE              1
```

### 디버그 출력 배선

| STM32 | 대상 |
|---|---|
| PA2 (USART2 TX) | USB-TTL 어댑터의 RX |
| GND | USB-TTL 어댑터의 GND |

115200 8N1, 송신 전용이다. USART1을 사용하지 않는 이유는 TX가 PA9로
좌측 엔코더 B상과 충돌하고, USART3은 PB10/PB11로 IMU와 충돌하기 때문이다.
PA2는 현재 핀맵에서 유일하게 충돌이 없는 선택지다.

```
screen /dev/ttyUSB0 115200
# 또는
minicom -D /dev/ttyUSB0 -b 115200
```

### 측정 절차

1. 차체를 들어 양쪽 바퀴가 자유롭게 회전하도록 한다.
2. 한쪽 바퀴에 시작점을 표시한다.
3. 표시한 바퀴를 **천천히 정확히 10회전** 정방향으로 돌린다.
4. LED 점등 시점과 터미널 출력을 확인한다.

### 판정 기준

터미널 출력은 다음과 같은 형태다.

```
L    57640 (11PPR 10.000rev  13PPR 8.461rev)   R        0 (11PPR 0.000rev  13PPR 0.000rev)
```

10회전을 마친 시점의 `rev` 값이 10.000에 가까운 쪽이 실제 PPR이다.

| 10회전 시점 관측 | 결론 | `COUNTS_PER_WHEEL_REV` |
|---|---|---|
| 11PPR 열이 10.000 부근 | ENC_PPR = 11 | 5764 |
| 13PPR 열이 10.000 부근 | ENC_PPR = 13 | 6812 |
| 어느 쪽도 아님 | 감속비 자체가 131이 아님 | 실측값 직접 대입 |

USB-TTL 어댑터가 없는 경우 LED만으로도 판정할 수 있다.
LED는 좌측 엔코더가 57640 카운트(11 PPR 가정 시 10회전)를 넘는 순간 점등한다.

- 정확히 10회전 지점에서 점등 → **11 PPR**
- 약 8.5회전 지점에서 점등 → **13 PPR**

### 방향 확인

정방향 회전 시 카운트가 **증가**해야 한다. 감소하는 축이 있으면
`config/board_config.h`의 `ENC_L_INVERT` 또는 `ENC_R_INVERT`를 반전시킨다.

### 좌우 대조

양쪽을 각각 측정하여 값이 크게 다르면 감속비가 다른 모터가 섞였거나
배선이 잘못된 것이다. 이 단계에서 반드시 확인한다.

### 측정 후

실측값을 `COUNTS_PER_WHEEL_REV`에 직접 대입하고 `CALIB_MODE`를 0으로
되돌린 뒤 재빌드한다. `GEAR_RATIO`를 역산할 필요는 없다.

**바닥에 내려놓기 전에 `CALIB_MODE`가 0인지 반드시 확인한다.**

## USB 링크

RPi5와의 통신은 USB CDC-ACM으로 구현했다. 호스트 측 드라이버 설치 없이
`/dev/ttyACM0`으로 인식된다.

### 프로토콜

```
[0xAA][0x55][TYPE][LEN][PAYLOAD ...][CRC16]
```

- 모든 다중 바이트 필드는 리틀 엔디언이다. Cortex-M3와 RPi5 양쪽 모두
  리틀 엔디언이므로 바이트 스왑이 발생하지 않는다.
- CRC16-CCITT(다항식 0x1021, 초기값 0xFFFF)를 TYPE, LEN, PAYLOAD에 적용한다.
- 최대 프레임은 62바이트로, 64바이트 벌크 전송 1회에 들어간다.
- 물리량은 부동소수점이 아닌 스케일된 정수로 전송한다. MCU에 FPU가 없고,
  고정소수점이 프레임 크기와 호스트 파싱 양쪽에 유리하다.

`lib/control/protocol.h`가 단일 진실 공급원이며, 브릿지 저장소의
`PROTOCOL.md`가 이를 반영한다.

### 메시지 종류

| TYPE | 방향 | 이름 | 페이로드 |
|---|---|---|---|
| 0x01 | 호스트 → MCU | `CMD_VELOCITY` | 4B, 선속도/각속도 |
| 0x02 | 호스트 → MCU | `CMD_WHEEL_RAW` | 4B, 좌우 듀티 직접 |
| 0x03 | 호스트 → MCU | `CMD_ESTOP` | 0B |
| 0x04 | 호스트 → MCU | `CMD_RESET_ODOM` | 0B |
| 0x05 | 호스트 → MCU | `CMD_CLEAR_FAULT` | 0B |
| 0x06 | 호스트 → MCU | `CMD_PING` | 0B |
| 0x81 | MCU → 호스트 | `TELEMETRY` | 48B, 50Hz |
| 0x86 | MCU → 호스트 | `PONG` | 0B |
| 0x87 | MCU → 호스트 | `BOOT_INFO` | 8B, 포트 오픈 시 1회 |
| 0x07 | 호스트 → MCU | `CMD_DIAG` | 0B, 진단 요청 |
| 0x88 | MCU → 호스트 | `DIAG` | 16B, 요청 시 |
| 0x08 | 호스트 → MCU | `CMD_I2C_SCAN` | 0B, 버스 스캔 요청 |
| 0x89 | MCU → 호스트 | `I2C_SCAN` | 17B, 스캔 결과 비트맵 |

`BOOT_INFO`는 `COUNTS_PER_WHEEL_REV`와 트랙 폭을 함께 전송한다.
호스트가 오도메트리 스케일을 하드코딩하지 않아도 되며, 모터 교체 시
브릿지가 자동으로 따라온다.

### 스케일링

| 물리량 | 단위 | 타입 |
|---|---|---|
| 선속도 | mm/s | int16 |
| 각속도 | mrad/s | int16 |
| 듀티 | permille | int16 |
| 위치 | mm | int32 |
| 방위 | mrad | int32 |
| 쿼터니언 | 1/16384 | int16 (BNO055 원본) |
| 자이로 | 1/16 deg/s | int16 (BNO055 원본) |
| 거리 | mm | uint16 (0xFFFF = 무효) |
| 배터리 | mV | uint16 (ADC 미구현, 현재 0) |

### 설계 원칙

**명령은 ACK하지 않는다.** 호스트가 `cmd_vel`을 연속 발행하므로 유실된
명령은 다음 주기에 자동 복구되며, 실제 링크 단절은 `drive.c`의 명령
타임아웃이 처리한다.

**텔레메트리는 큐잉하지 않고 폐기한다.** 이전 패킷이 전송 중이면 해당
프레임을 버린다. 지연 도착한 오래된 값은 누락보다 해롭고, 다음 프레임이
20ms 뒤에 오기 때문이다.

**E-stop은 래치된다.** 이후의 속도 명령으로 해제되지 않으며,
`CMD_CLEAR_FAULT`를 명시적으로 보내야 복귀한다.

**`CMD_WHEEL_RAW`는 PID를 우회한다.** 브링업 시 배선/기어 문제와 제어
튜닝 문제를 분리하기 위한 경로다. 일반 속도 명령을 받으면 자동 해제된다.

## 호스트 콘솔 도구

`tools/s2m_console.py`로 브릿지 노드 없이 펌웨어를 검증할 수 있다.

```
pip install pyserial

./tools/s2m_console.py                    # 텔레메트리 실시간 출력
./tools/s2m_console.py --ping             # 응답 확인
./tools/s2m_console.py --raw 300 300      # 듀티 30% 직접 인가
./tools/s2m_console.py --vel 100 0        # 100mm/s 직진
./tools/s2m_console.py --step 150         # 스텝 응답 CSV 캡처
./tools/s2m_console.py --estop            # 비상 정지
./tools/s2m_console.py --clear            # 폴트 해제
```

이 도구의 프레임 인코딩은 펌웨어 구현과 바이트 단위로 대조 검증되었다.

### USB 열거 실패 시

호스트에 "알 수 없는 USB 장치 (장치 설명자 요청 실패)" 또는 코드 43이
표시되는 경우, 장치가 버스에 감지는 되었으나 첫 컨트롤 전송에 응답하지
못한 상태다. D+ 풀업은 정상이라는 뜻이므로 배선보다 펌웨어를 먼저 의심한다.

과거 이 증상을 유발했던 원인은 다음 두 가지다.

**PMA 주소 계산 오류.** PMA는 512바이트 패킷 메모리이나 CPU에서는
16비트 값이 32비트 간격으로 보인다. 바이트 오프셋 N은 `PMA_BASE + N*2`에
위치한다. `PMA()` 매크로가 이미 2를 곱하므로 호출부에서 다시 나누면
모든 버퍼가 의도한 주소의 절반에 배치되어, EP0 TX 데이터가 EP0 RX
버퍼를 덮어쓴다.

**COUNT_RX 블록 크기 인코딩 오류.** `COUNT_RX`는 수신 길이가 아니라
버퍼 크기를 압축 형식으로 담는다. 비트 15가 블록 단위를, 비트 14:10이
블록 개수를 지정한다. 64바이트는 `BL_SIZE=1`(32바이트 블록)에
`NUM_BLOCK=2`이므로 `0x8800`이다. `NUM_BLOCK=1`로 두면 32바이트 버퍼가
되어 최대 크기 패킷마다 오버런이 발생한다.

VMware 환경에서는 게스트로의 USB 패스스루도 확인한다. STM32는 ST-LINK와
별개의 장치로 열거되므로 `VM → Removable Devices`에서 별도로 연결해야 한다.

### 브링업 순서

1. `--ping`으로 링크를 확인한다. `BOOT_INFO`가 5764 counts/rev를
   보고하면 정상이다.
2. **차체를 들어 바퀴를 띄운다.** `--raw`는 PID를 우회하므로 바닥에
   놓인 상태로 실행하면 즉시 주행한다.
3. `--raw 300 0`을 실행한다. 확인 항목은 세 가지다.

   | 확인 | 정상 | 불일치 시 |
   |---|---|---|
   | 좌측 바퀴가 도는가 | 예 | 커넥터 좌우 교체 |
   | 전진 방향인가 | 예 | `MOTL_INVERT` 반전 |
   | `spd_l`이 양수인가 | 예 | `ENC_L_INVERT` 반전 |

4. `--raw 0 300`으로 우측도 동일하게 확인한다.
5. `--step 150`으로 스텝 응답을 캡처하여 PID를 튜닝한다.

명령한 쪽과 다른 바퀴가 회전하는 경우 좌우 커넥터가 교차된 것이다.
이때는 코드가 아닌 배선을 바로잡는다. 핀맵과 물리 배치가 어긋나면
이후 IMU 축 정합과 슬립 검출에서 부호가 꼬인다.

### 방향 설정 (실측 완료)

2026-08-14 실측으로 확정했다.

| 항목 | 값 | 근거 |
|---|---|---|
| `MOTL_INVERT` | 0 | 좌측 모터는 정방향 회전 |
| `MOTR_INVERT` | 1 | 우측 모터는 미러 장착 |
| `ENC_L_INVERT` | 1 | 전진 시 카운트 감소 |
| `ENC_R_INVERT` | 0 | `MOTR_INVERT`가 구동 방향을 이미 보정 |

우측은 모터 반전과 엔코더 반전을 함께 적용하면 부호가 두 번 뒤집혀
원래대로 돌아온다. 모터만 반전하는 것이 맞다.

모터 반전은 `motor_set()` 단일 진입점에서 적용한다. 슬루 제한,
방향 전환 데드타임, 스톨 가드가 모두 실제 하드웨어에 인가되는 부호를
기준으로 동작해야 하기 때문이다.

텔레메트리의 `duty_l`, `duty_r`은 **반전 적용 전의 논리 듀티**를
보고한다. 전진 명령 시 양쪽 모두 양수로 표시되며, 전기적 부호는
모터 장착 방향에 따른 구현 세부사항으로 간주한다.

## IMU (BNO055)

### 배선

| STM32 | BNO055 |
|---|---|
| PB10 | SCL (I2C2) |
| PB11 | SDA (I2C2) |
| 5V | VIN (모듈 레귤레이터 경유) |
| GND | GND |

I2C 주소는 0x28이다. COM3 핀을 상승시킨 경우 0x29이며
`config/board_config.h`의 `BNO055_ADDR`을 수정한다.

풀업 저항은 모듈에 내장된 것을 사용한다.

### 동작 방식

NDOF 모드로 구동하여 센서 융합을 BNO055 자체 프로세서가 수행한다.
MCU는 결과만 읽는다. 융합을 STM32에서 수행하는 것은 이 부품의 존재
이유를 낭비하는 것이며, RAM 20KB 제약에도 맞지 않는다.

융합 출력은 100Hz로 갱신되므로 `IMU_PERIOD_MS`는 10으로 설정한다.
그보다 빠르게 폴링하면 동일한 값을 반복해서 읽으며 버스만 점유한다.

쿼터니언 4워드는 **단일 버스트로 읽는다.** 개별적으로 읽으면 읽는 도중
장치가 값을 갱신하여 실재하지 않는 자세가 조합될 수 있다.

### 논블로킹 설계

I2C 전송은 메인 루프에서 구동되는 상태머신으로 구현했다. 블로킹 방식은
9바이트 읽기에 100kHz 기준 약 1ms가 소요되어 200Hz 제어 루프를
직접 잠식한다.

초기화 시퀀스 역시 상태머신이다. BNO055는 전원 인가 후 응답까지 약
700ms, 모드 전환에 20ms가 필요한데, 이를 블로킹 지연으로 처리하면
워치독 리셋이 발생하고 주행 제어가 정지한다.

### I2C 버스 복구

**STM32F1의 I2C 페리페럴은 락업이 발생한다.** 전송 도중 중단되면
슬레이브가 SDA를 계속 Low로 유지하며, 페리페럴 레지스터 조작으로는
해소되지 않는다.

유일한 해결책은 다음 순서다.

1. 핀을 GPIO 오픈드레인으로 전환
2. 슬레이브가 SDA를 놓을 때까지 SCL을 수동으로 최대 9회 토글
3. 수동으로 STOP 조건 생성 (SCL High 상태에서 SDA 상승)
4. 페리페럴 소프트웨어 리셋

`i2c_bus_recover()`가 이를 수행한다. 이 부품에서는 선택 사항이 아니다.

복구는 다음 시점에 자동 실행된다.

- 초기화 시 SDA가 Low로 감지된 경우 (이전 리셋의 잔재)
- 전송 단계가 5ms를 초과한 경우
- 연속 10회 읽기 실패

버스 속도는 400kHz가 아닌 **100kHz**를 사용한다. BNO055의 클럭
스트레칭과 F1 에라타의 조합이 저속에서 훨씬 안정적이며, 100Hz 융합
데이터에는 100kHz로 충분하다.

### 캘리브레이션

BNO055는 지자계 캘리브레이션이 완료되어야 절대 방위가 정확하다.
캘리브레이션 상태는 매 폴링 주기에 함께 읽어 텔레메트리 상태 필드의
`STATUS_IMU_CALIBRATED` 비트로 보고한다.

캘리브레이션 방법은 다음과 같다.

1. 차체를 8자 형태로 수 회 천천히 움직인다 (지자계)
2. 정지 상태로 수 초간 유지한다 (자이로)
3. 여섯 방향으로 각각 세워 정지한다 (가속도계)

캘리브레이션 이전에도 상대적 자세 변화는 사용 가능하나 절대 방위는
드리프트할 수 있으므로, 상위 SBC는 이 비트를 참조하여 가중치를 조정한다.

### I2C 버스 스캔

주소를 추측하는 대신 실제로 응답하는 장치를 확인한다.

```
./tools/s2m_console.py --scan
```

```
[i2c scan] 1 device(s) responded
  0x29  BNO055 (ADR high)
  -> set BNO055_ADDR to 0x29 in board_config.h
```

응답이 없으면 전원, 배선, 풀업 저항 순으로 확인한다.
0x29만 응답하면 모듈의 ADR 핀이 상승 상태이므로
`config/board_config.h`의 `BNO055_ADDR`을 0x29로 수정한다.

응답이 없을 때는 버스 라인 상태를 함께 보고한다.

```
[i2c scan] 0 device(s) responded
  BUS LINES NOT IDLE HIGH -- no scan is possible.
  A line held low means one of:
    - no pull up resistors on SCL/SDA
    - the sensor board has no power
    - SCL or SDA shorted to ground
```

라인이 정상인데 응답이 없으면 센서 전원과 GND 공통 여부를 확인한다.

**스캔 타임아웃 설계.** 초기 구현은 가드 루프를 100000회로 설정하여,
버스에 아무것도 없을 때 전체 스캔이 2.3초를 소요했다. 이 동안 메인
루프가 정지하여 USB 연결이 끊기고 워치독이 발동했으며, 결과적으로
콘솔에 아무 출력도 나타나지 않았다.

현재는 다음과 같이 조정했다.

- 가드 루프를 20000회(약 1.4ms)로 축소
- 모든 대기 루프 내부에서 워치독 갱신
- 연속 8회 타임아웃 시 스캔 조기 종료

정상 버스에서는 약 12ms, 완전히 죽은 버스에서도 50ms 이내에 종료된다.

### 진단

IMU가 동작하지 않을 때는 다음 명령으로 초기화 상태를 확인한다.

```
./tools/s2m_console.py --diag
```

출력 예시는 다음과 같다.

```
[diag] imu init stage : CHECK_ID
       chip id        : 0xA0 (BNO055 ok)
       calib sys/g/a/m: 3/3/3/2
       reads ok/fail  : 1234 / 5
       i2c err/recover: 7 / 2
```

| 증상 | 원인 |
|---|---|
| `WAIT_BOOT`에서 정지, chip id 0xFF | 응답 없음. 배선 또는 전원 확인 |
| `CHECK_ID`에서 `FAILED`, chip id가 0xA0이 아님 | 주소 불일치 또는 다른 장치 |
| `COMPLETE`인데 read fail 증가 | 버스 불안정. 풀업 저항 확인 |
| `i2c recover` 계속 증가 | 슬레이브가 SDA를 잡고 있음 |

chip id가 0xFF로 유지되면 장치가 전혀 응답하지 않는 것이다.
확인 순서는 다음과 같다.

1. BNO055 모듈에 전원이 인가되는지 (VIN 5V, GND 공통)
2. SCL이 PB10, SDA가 PB11에 연결되었는지 (교차 연결 흔함)
3. I2C 주소가 0x28인지 0x29인지 (모듈의 ADR/COM3 핀 상태)
4. 풀업 저항이 존재하는지 (모듈 내장 여부 확인)

### 확인 방법

```
./tools/s2m_console.py --imu
```

`yaw`와 `gz` 컬럼이 추가된다. 차체를 손으로 회전시켰을 때 `yaw`가
따라 변하고, 회전 중에만 `gz`가 0이 아닌 값을 보이면 정상이다.

상태 필드에 `IMU_OK`가 표시되지 않으면 배선 또는 주소를 확인한다.

## 제어 구조

```
목표 속도 (v, w)
   -> 차동 구동 역기구학 -> 좌/우 목표 휠 속도
   -> 피드포워드 (PID_FF) + 속도 PID
   -> 듀티 permille -> 슬루 제한 -> PWM
```

피드포워드가 출력의 대부분을 담당하고 PID는 잔차만 보정한다.
이 구조는 게인을 작게 유지할 수 있어 정정 특성이 안정적이다.

미분항을 사용할 경우 `PID_KD`와 함께 `PID_USE_D`를 1로 설정한다.
전처리기는 부동소수점 비교를 수행할 수 없으므로 별도 스위치가 필요하다.

### 게인 산정 근거

2026-08-14 무부하 스텝 응답 실측 결과 목표 150 mm/s에 대해 172 mm/s로
정착하여 약 15%의 정상상태 오차가 제거되지 않았다. 원인은 두 가지였다.

**게인이 과소했다.** `PID_KP = 180`은 22 mm/s 오차에 대해 4 permille의
보정만 요청한다. 적분항 역시 `PID_KI = 90`으로 오차를 해소하는 데 약
48초가 소요되어 사실상 무효했다.

산정 기준은 다음과 같다. 전듀티가 `MAX_WHEEL_SPEED_MPS`에 대응하므로,
속도 오차 10%가 듀티 보정 10%를 유발하려면 `KP`는
`DUTY_MAX / MAX_WHEEL_SPEED_MPS` 규모가 되어야 한다.

**안티 와인드업이 적분값을 파괴했다.** 기존 구현은 출력 포화 시 적분값을
절반으로 잘랐다. 이는 와인드업 방지가 아니라 적분기 리셋이며, 이미 축적한
보정을 매 루프 폐기하므로 정상상태 오차가 영구히 남는다.

조건부 적분(conditional integration)으로 교체했다. 포화 상태에서 포화를
악화시키는 방향일 때만 누적을 중단하고, 축적된 값은 보존한다.

| 상수 | 초기값 | 확정값 |
|---|---|---|
| `PID_KP` | 180 | 3000 |
| `PID_KI` | 90 | 4500 |
| `PID_I_LIMIT` | 400 | 600 |
| `PID_FF` | 3800 | 5000 |
| `SPEED_WINDOW` | - | 4 |

### 튜닝 결과 (2026-08-14, 확정)

목표 150 mm/s 계단 입력에 대한 응답이다.

| 항목 | 1차 무부하 | 2차 무부하 | 3차 지면 | **4차 지면(확정)** |
|---|---|---|---|---|
| 정상상태 오차 (좌) | 14.9% | 5.7% | 2.0% | **0.3%** |
| 정상상태 오차 (우) | 13.1% | 4.9% | 1.8% | **0.3%** |
| 2% 대역 진입 | - | - | 2180 ms | **760 ms** |
| 90% 도달 | 260 ms | 240 ms | 300 ms | 340 ms |
| 오버슈트 | 0% | 10.0% | 5.3% | **5.3%** |
| 좌우 편차 | 2.6 | 1.2 | 0.4 | **0.0 mm/s** |
| 정착 듀티 | 744 | 673 | 734 | 769 |

`PID_KI`를 3000에서 4500으로 상향한 결과 **정착 시간이 2.9배 단축**되었으며
오버슈트는 변화가 없었다. 적분항이 느린 수렴 구간만을, 비례항이 과도
응답을 지배한다는 예측과 일치한다.

최종 정상상태 오차 0.4 mm/s는 **속도 측정 양자(1.8 mm/s)보다 작다.**
정착 구간 표준편차 역시 1.08 mm/s로 양자 이내이므로 사실상 완전 수렴에
해당한다. 측정 방식을 변경하지 않는 한 추가 튜닝은 의미가 없다.

좌우 편차는 0.0 mm/s로, 모터 개체차에 의한 직진 편향은 존재하지 않는다.

**피드포워드 검증.** 지면에서 150 mm/s 유지에 734 permille이 필요했고,
`PID_FF = 5000`의 예측값은 750 permille로 오차 16 permille이다.
무부하 시에는 673 permille이 필요하여 격차가 77 permille이었다.
정격 회전수 기준으로 `PID_FF`를 산정한 것이 옳았음을 확인한다.

### 속도 측정 분해능

엔코더 1카운트는 0.036 mm이나, 5ms 제어 주기로 차분하면 속도 분해능은
**7.2 mm/s**가 된다. 150 mm/s 기준 4.8%로, PID가 제거하려는 정상상태
오차보다 거칠다. 실측에서 정착 속도가 158과 165 사이를 오간 것은 인접한
양자 두 칸 사이의 디더링이며 게인으로 개선할 수 없다.

속도 산출에 `SPEED_WINDOW = 4` 롤링 윈도우를 적용하여 분해능을
**1.8 mm/s(1.2%)** 로 개선했다. 위상 지연은 약 10ms 증가하나, 플랜트
시정수 110ms 대비 무시할 수준이다.

| 윈도우 | 분해능 | 150mm/s 대비 | 지연 |
|---|---|---|---|
| 1 (5ms) | 7.2 mm/s | 4.8% | 0 |
| 2 (10ms) | 3.6 mm/s | 2.4% | 2.5ms |
| **4 (20ms)** | **1.8 mm/s** | **1.2%** | **7.5ms** |
| 8 (40ms) | 0.9 mm/s | 0.6% | 17.5ms |

오도메트리는 이 윈도우의 영향을 받지 않는다. 매 루프의 정확한 카운트를
그대로 적분한다.

**튜닝은 반드시 지면에서 수행한다.** 무부하 상태에서는 피드포워드가 약
16% 과다하여 적분항이 이를 상쇄하는 데 수 초가 소요되며, 이는 튜닝 결함이
아니라 부하 부재로 인한 현상이다.

## 속도 및 각속도 제한

| 항목 | 상수 | 값 | 근거 |
|---|---|---|---|
| 최고 병진 속도 | `MAX_WHEEL_SPEED_MPS` | 0.20 m/s | 정격 58RPM |
| 최대 각속도 | `MAX_ANGULAR_RATE` | 0.80 rad/s | 스캔 품질 |
| 기구적 각속도 한계 | `MAX_ANGULAR_RATE_MECH` | 1.67 rad/s | 참고값 |

제자리 회전 시 기구적 한계는 다음과 같다.

```
w = 2 x v / track = 2 x 0.20 / 0.24 = 1.67 rad/s (약 96 deg/s)
```

RPLiDAR C1의 1회전 주기는 100ms이므로, 96 deg/s로 회전하면 단일 스캔이
약 9.6도 왜곡된다. 스캔 매칭 품질이 저하되므로 명령 각속도는 기구적
한계보다 낮은 0.80 rad/s(약 46 deg/s)로 제한한다.

매핑 정확도보다 기동성이 중요한 상황에서는 이 값을 상향할 수 있으나,
`MAX_ANGULAR_RATE_MECH`를 초과하는 설정은 의미가 없다.

### 방향 전환 데드타임

BTS7960의 하프브리지 관통을 막기 위해 방향 전환 시 양쪽 출력을 0으로
두는 구간을 삽입한다. 이 로직은 매 루프 조건 검사가 아니라 **명시적
상태**로 구현되어 있다.

초기 구현은 매 루프마다 반전 조건을 재평가했다. 슬루 제한이 `applied`를
새 부호 방향으로 한 단계 이동시키면 반전 조건이 성립하여 `applied`가
다시 0으로 강제되고, `sign`이 0이 되었으므로 `last_sign`도 갱신되지
않았다. 그 결과 **방향 전환 시 해당 바퀴가 영구히 정지**했다.

이 결함은 한쪽 모터를 미러 장착으로 설정한 뒤에야 실물에서 드러났다.
`test/test_motor.c`가 이 케이스를 회귀 검증한다.

## 안전 설계

| 항목 | 설정값 | 비고 |
|---|---|---|
| 비상 정지 경로 | EN 핀 Low | PWM 레지스터가 아닌 EN 핀으로 처리 |
| 슛스루 차단 | 상시 | RPWM/LPWM 중 한쪽은 항상 0 |
| 방향 전환 데드타임 | 2ms | 하프브리지 관통 방지 |
| 듀티 슬루 제한 | 루프당 2% | 기어박스 및 전원 새그 보호 |
| 명령 타임아웃 | 300ms | RPi5 무응답 시 자동 정지 |
| 스톨 가드 | 고듀티 3초 | 모터 소손 방지 |
| 엔코더 헬스체크 | 무응답 1초 | 개루프로 자동 전환 |
| 적분 와인드업 방지 | 포화 시 클램프 | `PID_I_LIMIT` |
| IWDG | 약 400ms | 펌웨어 행(hang) 방지 |

부팅 시퀀스는 `motor_init()`이 EN을 Low로 내리고 PWM을 0으로 설정한 뒤에야
`motor_enable()`이 호출되도록 구성했다. 리셋 직후 바퀴가 돌발 구동되는
상황을 방지한다.

## 하드웨어 주의사항

- 보드의 VBUS 패턴을 반드시 절단한다. 전원은 UBEC 5V 레일에서 공급한다.
- 모터 GND와 로직 GND는 단일 스타 접지점에서 만나도록 배선한다.
- BTS7960의 IS 핀(R_IS/L_IS)은 과전압 위험으로 미연결 상태를 유지한다.
- 각 IC 근처에 0.1uF 디커플링 캐패시터를 배치한다.
- 거리센서 전원부에 10~100uF 벌크 캐패시터를 추가한다.
- 엔코더 신호선은 모터 전원선과 분리하여 포설한다. 나란히 묶으면
  브러시 노이즈가 유도되어 위상 오검출이 발생한다.

## 보드 고유 사항

### 상태 LED는 PC13이 아니라 PB12다

본 프로젝트가 사용하는 STM32F103C8T6 코어보드는 표준 Blue Pill이 아니다.
회로도상 사용자 LED(D2, 실크 `측试`)는 R6 1K를 거쳐 **PB12**에 연결되며,
PC13에는 아무것도 연결되지 않는다. 전원 LED(D1)는 VCC3.3에 직결되어
항상 점등된다.

일반적인 Blue Pill 예제 코드는 PC13을 가정하므로 그대로 사용하면
LED가 전혀 반응하지 않는다. 이 차이를 확인하지 않으면 펌웨어가
정상 동작 중임에도 "아무것도 실행되지 않는다"고 오판하기 쉽다.

LED 관련 코드는 `lib/hal/led.c`로 분리했으며, 포트와 핀, 극성은
`config/board_config.h`의 다음 세 매크로에서만 정의한다.

```
#define LED_PORT                GPIOB
#define LED_PIN                 12U
#define LED_ACTIVE_LOW          1
```

다른 리비전의 보드를 사용할 경우 이 세 값만 수정한다.

### 점멸 패턴으로 실행 단계 식별

터미널 없이도 펌웨어가 어느 단계까지 진행했는지 확인할 수 있도록
부팅 시 점멸 횟수를 구분했다.

| 패턴 | 의미 |
|---|---|
| 2회 점멸 | `main()` 진입 완료 |
| 이어서 3회 점멸 | 캘리브레이션 모드 진입 |
| 2회씩 반복 점멸 | 클럭 오류: HSE 미발진 (크리스탈, C5/C6 확인) |
| 4회씩 반복 점멸 | 클럭 오류: PLL 미잠금 (설정 오류) |
| 500ms 주기 점멸 | 정상 주행 모드 동작 중 |
| 무반응 | 플래시 실패 또는 전원 문제 |
| 불규칙하게 계속 깜빡임 | 워치독 리셋 루프 (아래 참조) |

### 워치독과 블로킹 구간

IWDG 타임아웃은 400ms다. **이보다 오래 걸리는 블로킹 구간은 반드시
내부에서 `IWDG->KR`에 리프레시 키를 써야 한다.** 그렇지 않으면 동작
도중 리셋이 걸려 부팅을 무한 반복하며, 증상이 클럭 오류와 유사하게
보이므로 원인 파악이 어렵다.

현재 다음 함수들이 내부에서 워치독을 리프레시한다.

| 함수 | 이유 |
|---|---|
| `led_blink_blocking()` | 3회 점멸에 약 900ms 소요 |
| `systick_delay_ms()` | 호출자가 지연 시간을 신경쓰지 않도록 |
| `clock_fault_handler()` | 오류 코드를 계속 표시해야 함 |

반대로 `Default_Handler()`는 **의도적으로 리프레시하지 않는다.**
정의되지 않은 벡터에 진입한 것은 펌웨어 상태가 불명확하다는 뜻이므로,
워치독이 보드를 리셋하도록 두는 것이 올바른 동작이다.

## 검증 절차

1. **부팅 확인**: 리셋 직후 LED가 2회 점멸하는지 확인한다.
   점멸이 없으면 플래시가 실패했거나 전원이 공급되지 않은 것이다.
   빠른 연속 점멸이 계속되면 크리스탈이 발진하지 않은 것이다.
2. **PWM 확인**: PA0/PA1에서 20kHz 신호가 출력되는지 측정한다.
3. **엔코더 방향 확인**: 바퀴를 손으로 정방향 회전시켰을 때
   `encoder_get_total()`이 증가하는지 확인한다. 감소하면 해당 축의
   `ENC_x_INVERT`를 반전시킨다.
5. **엔코더 분해능 실측**: 위 절차에 따라 `COUNTS_PER_WHEEL_REV`를 확정한다.
   데이터시트 기준 계산값은 11 x 4 x 131 = 5764 이다.
6. **모터 방향 확인**: 바퀴를 띄운 상태로 확인한다. 방향이 반대인 경우
   배선이 아니라 `MOTL_INVERT` / `MOTR_INVERT`를 조정한다.
7. **PID 튜닝**: `--step`으로 계단 응답을 캡처한다. 무부하 검증 후
   반드시 지면 주행 상태에서 재확인한다.

## 향후 작업 순서

| 순서 | 모듈 | 상태 |
|---|---|---|
| 1 | USB CDC | 구현 완료, 실물 검증 대기 |
| 2 | 바이너리 프로토콜 | 구현 완료, 호스트 교차 검증 완료 |
| 3 | PID 튜닝 | 실물 스텝 응답 필요 |
| 4 | BNO055 드라이버 | 구현 완료, 실물 검증 대기 |
| 5 | ADC 거리센서 | 미구현, 0xFFFF 반환 중 |
| 6 | 배터리 전압 감시 | 미구현, 프레임 자리만 확보 |
| 7 | 슬립 검출 | 엔코더 오도메트리와 IMU 요레이트 비교 |

STM32는 센서 융합을 수행하지 않는다. 원시값에 타임스탬프만 부여하여
전송하고, `sensor_msgs/Imu` 및 `nav_msgs/Odometry` 변환과 TF 처리는
상위 SBC(RPi5)에서 담당한다. 펌웨어 내부의 오도메트리 적분은 슬립 검출과
디버깅 편의를 위한 보조 수단이며, SLAM의 입력으로 사용하는 값은 아니다.
